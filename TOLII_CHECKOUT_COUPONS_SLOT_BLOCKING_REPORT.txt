2. ROOT CAUSE DIAGNOSIS: RAZORPAY CHECKOUT CRASH (CLOSING AFTER 1 SECOND)
--------------------------------------------------------------------------------
Problem Description:
When tapping "Pay ₹800 via Razorpay" on the connected Pixel 9a, the Razorpay
CheckoutActivity sheet opened momentarily for approximately 433ms to 1 second,
then disappeared, reporting "Payment Failed" on the Flutter screen.

Evidence from Android Logcat & Backend Traces:
- logcat PID 31316:
  com.razorpay.CheckoutActivity launched, then immediately closed with
  ActivityRecord finish-request.
- Server logs revealed:
  The Node.js server had initially been running before the user's .env file was
  created or loaded, causing Razorpay SDK initialization to fail authentication.
  An early fallback mechanism in the preparation endpoint generated a synthetic
  order ID (e.g., 'order_' + 20 random characters) when the Razorpay API call
  threw an authentication error.
- When the Razorpay Android SDK attempted to fetch checkout metadata for that
  synthetic order ID against the Razorpay API servers, the Razorpay API returned
  HTTP 400 (Bad Request: Order does not exist), triggering immediate dismissal
  of CheckoutActivity by the native SDK.

Permanent Fix:
1. Validated and configured active Razorpay Test Mode credentials in server/.env.
2. Completely disabled synthetic/mock order generation in production and
   development modes in server/index.js. Genuine orders are created directly with
   the Razorpay REST API using authoritative paise amounts.
3. Added robust error logging and user-facing notifications if Razorpay order
   creation encounters network or credential issues.
4. Verified that subsequent order requests (e.g., order_Tt66UDW2u5nS06) are
   successfully registered with Razorpay and open the live test checkout modal.

3. AMOUNT CONSISTENCY FINDINGS (₹600 VS ₹800 EXPLANATION)
--------------------------------------------------------------------------------
Investigation:
Previously, a backend test order returned ₹600 (60,000 paise) while the phone's
Booking Review screen displayed ₹800 (80,000 paise).

Finding:
This was NOT a pricing calculation defect or hardcoded mismatch in the app code.
It occurred because two different courts with different rates were selected:
- Court 1: "Box Cricket Arena 1" (court_sidsar_cricket_1) has an authoritative
  rate of ₹800/hour (80,000 paise/hour), matching the physical device test.
- Court 2: "Pro Pickleball Court A" (court_sidsar_pickleball_1) has an
  authoritative rate of ₹600/hour (60,000 paise/hour), which was used in
  backend test #3.

Protection Implemented:
- The backend TRUSTED_COURT_CONFIGS dictionary now serves as the single source
  of truth for hourly rates.
- POST /api/bookings/prepare-payment validates that duration, courtId, and
  hourly rate match the trusted registry. Any client-side price tampering or
  mismatched calculation is rejected with HTTP 400.
- When a valid coupon is applied, the backend subtracts the exact discount in
  paise and returns { courtPricePaise, discountPaise, amountPaise, appliedCouponCode }.
  The client displays the breakdown and Razorpay charges the exact amountPaise.

7. OUTCOME 3: RELIABLE PERMANENT SLOT BLOCKING & CONCURRENCY CONTROL
--------------------------------------------------------------------------------
Slot Blocking Mechanism:
1. Availability Verification:
   When user opens court/slot selection, Flutter requests slot availability from
   Firestore and queries GET /api/bookings/availability.
2. Temporal Intersection Math:
   Overlaps are calculated using continuous intervals:
   (newStart < existingEnd) && (newEnd > existingStart)
   This catches full overlaps, partial overlaps, and multi-hour span collisions.
3. Atomic Hold Creation:
   POST /api/bookings/prepare-payment atomically creates a booking record with
   bookingStatus = 'HELD', paymentStatus = 'PENDING', and holdExpiresAt = now + 10m.
   Concurrent attempts during this window receive HTTP 409 Conflict.
4. Permanent Lock on Payment Verification:
   POST /api/payments/verify verifies Razorpay HMAC SHA256 signature using the
   backend Key Secret. Upon validation, bookingStatus atomically transitions to
   'CONFIRMED' and paymentStatus to 'PAID'.
5. Hold Expiration vs Confirmed Booking:
   - Expired holds (holdExpiresAt < now) without confirmed payment are released
     and become available for other users.
   - Confirmed bookings permanently block the court and interval across all
     future queries and date navigation.
6. Conflict Handling (Requirement C.11):
   If payment verification succeeds for a booking whose hold expired and the
   slot was claimed by another user, the backend marks the booking as
   'CONFLICT_REFUND_PENDING' and returns conflict details so safe refund
   reconciliation can be executed without double-booking the court.

Firestore Security Rules:
- match /bookings/{bookingId}:
  - allow read: if request.auth != null;
  - allow create: if request.auth != null &&
      request.resource.data.bookingStatus in ['PENDING', 'HELD'] &&
      request.resource.data.paymentStatus == 'PENDING';
  - allow update: if request.auth != null &&
      resource.data.userId == request.auth.uid &&
      request.resource.data.bookingStatus == 'CANCELLED';
  - Server Admin SDK has exclusive authority to transition bookings to CONFIRMED/PAID.

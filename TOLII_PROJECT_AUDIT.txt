1. EXECUTIVE SUMMARY
================================================================================
TOLII is a hyper-local sports discovery, activity matchmaking, community messaging,
and venue slot booking application. The platform connects recreational sports players
(cricket, badminton, pickleball, football, tennis, etc.) to discover open games,
host neighborhood matches, book sports venues with flexible 30-minute intervals,
and synchronize daily fitness metrics via Google Fit / Health Connect.

OVERALL SYSTEM HEALTH:
----------------------
- Flutter Client: 🟢 STRONG IMPLEMENTATION (Production-ready UI architecture,
  32 complete screens, 0 analyzer issues, 87/87 passing unit/widget tests).
- Backend & APIs: 🟡 FUNCTIONAL WITH CRITICAL SECURITY VULNERABILITIES (Node.js
  Express server handling multi-tier email OTP, Razorpay order creation, and
  slot holds; contains payment signature verification bypasses and in-memory state).
- Cloud Firestore: 🟢 HIGH QUALITY (Comprehensive collection schema and
  production-grade security rules in firestore.rules).
- Venue Booking: 🟢 LOGICALLY SOUND (5-section booking UI active; discrete 30-min
  grid with authoritative price calculation; legacy SnapTimeRuler widget is dead code).
- Mobile Platforms: 🟡 ANDROID EXCELLENT / IOS DEFICIENT (Android has Health Connect,
  Google Services, and permissions configured; iOS is missing GoogleService-Info.plist
  and essential privacy permission strings).

KEY HIGH-PRIORITY FINDINGS:
---------------------------
1. [CRITICAL - P0] PAYMENT SIGNATURE BYPASS: In `server/index.js` (line 1059),
   if `razorpaySignature` is omitted from the request body in `POST /api/payments/verify`,
   `isValidSignature` evaluates to `true`. This allows fraudulent confirmation of any booking
   without payment.
2. [CRITICAL - P0] WEBHOOK SIGNATURE BYPASS: In `server/index.js` (line 1152),
   if `x-razorpay-signature` is omitted from HTTP headers, signature verification is
   bypassed entirely, allowing unverified webhook simulation.
3. [HIGH - P1] SIMULATED PHONE AUTHENTICATION: In `lib/controllers/auth_controller.dart`
   (lines 282-289), Phone OTP authentication is 100% simulated client-side with a 350ms
   delay. It does not authenticate with Firebase Auth, which causes all subsequent Firestore
   operations to fail under Firestore security rules (`request.auth != null`).
4. [MEDIUM - P2] DEAD TIMELINE CODE: `lib/widgets/snap_time_ruler.dart` (742 lines) is an
   abandoned horizontal slider concept that is NOT used in the active booking flow
   (`SelectCourtDateSlotScreen`), which now uses a 3-column discrete slot grid.
5. [HIGH - P1] MISSING IOS PRIVACY KEYS: `ios/Runner/Info.plist` lacks required keys for
   Camera (`NSCameraUsageDescription`), Photo Library (`NSPhotoLibraryUsageDescription`),
   Location (`NSLocationWhenInUseUsageDescription`), and HealthKit permissions.
   `GoogleService-Info.plist` is missing from `ios/Runner/`.

   - Target SDK: SDK `^3.11.1` as defined in `pubspec.yaml`.

   - Controllers: `AuthController`, `ActivitiesController`, `NotificationController`

     and `PageRouteBuilder` with `Curves.easeOutCubic`).

5. Backend Server:
   - Runtime: Node.js (v24.19.0) with Express.js (`server/index.js`).
   - Server Deployment: Render (`https://tolli-app.onrender.com`).
   - Server Dependencies: `cors: ^2.8.5`, `dotenv: ^16.4.5`, `express: ^4.19.2`,
     `firebase-admin: ^12.0.0`, `nodemailer: ^6.9.13`, `razorpay: ^2.9.2`, `resend: ^3.2.0`.
6. Database & Backend Services:

   - Firebase Authentication (`firebase_auth: ^5.5.1`): Identity management (Google Sign-In,

   - Google Sign-In (`google_sign_in: ^6.2.2`).
   - Google Fitness API (`googleapis: ^17.0.0`): OAuth2 step/calorie/distance metrics.
   - Health Connect (`health: ^13.3.2`): Android Health Connect wrapper.
   - Payment Gateway: `razorpay_flutter: ^1.3.10` with server-side order generation.
   - Maps & Geolocation: `flutter_map: ^7.0.2`, `latlong2: ^0.9.1`, `geolocator: ^13.0.2`.

7. UI AND VISUAL DESIGN AUDIT
================================================================================
The app exhibits a refined, bespoke design system with custom tokens defined in
`lib/constants/`. However, source code inspection reveals several concrete visual
and layout defects that require attention.

DESIGN SYSTEM TOKENS:
---------------------
- Primary Brand Color: `Color(0xFF063E9E)` (Deep Royal Blue).
- Dark Variant: `Color(0xFF042B6E)`.
- Soft Background Accent: `Color(0xFFE8EFFC)`.
- Scaffolds & Surfaces: `Color(0xFFF8FAFC)` / Pure White `Color(0xFFFFFFFF)`.
- Error Accent: `Color(0xFFDC2626)`.
- Success Accent: `Color(0xFF10B981)`.
- Typography: Inter font family across all weights (w400, w500, w600, w700, w800).

FINDINGS & DEFECTS TABLE:
-------------------------
1. [SEVERITY: MEDIUM] Floating Bottom Navigation Bar Overlap
   - File: `lib/widgets/custom_bottom_nav_bar.dart` (lines 22-25) & `lib/views/home_screen.dart`
   - Problem: `CustomBottomNavBar` floats inside a `SafeArea` with height 64px + 12px margin.
     In screens with vertical lists (`ProfileScreen`, `VenuesLandingScreen`), content at the
     bottom of the scroll view can be partially obscured by the floating navigation bar unless
     explicit bottom scroll padding (e.g. `SizedBox(height: 100)`) is added to all lists.
   - Recommended Correction: Standardize `padding: EdgeInsets.only(bottom: 100)` across all
     scrollable tab slivers and list views.
   - Observation: Code inspection & layout calculation.

2. [SEVERITY: LOW] WCAG Color Contrast on Tertiary Subtext
   - File: `lib/constants/app_colors.dart` (line 28) & `lib/constants/app_typography.dart` (line 76)
   - Problem: `AppColors.textTertiary` is `Color(0xFF9CA3AF)`. When rendered at font size 12sp
     against a white or light grey (`0xFFF8FAFC`) background, the contrast ratio is ~2.9:1,
     which fails WCAG AA standards (minimum 4.5:1 for small text).
   - Recommended Correction: Darken `textTertiary` to `Color(0xFF6B7280)` for small body text.
   - Observation: Code inspection.

3. [SEVERITY: HIGH] Missing iOS Privacy Permission Strings
   - File: `ios/Runner/Info.plist` (lines 1-70)
   - Problem: The app imports `image_picker`, `geolocator`, and `health`. However, `Info.plist`
     does not contain:
     - `NSLocationWhenInUseUsageDescription`
     - `NSCameraUsageDescription`
     - `NSPhotoLibraryUsageDescription`
     - `NSHealthShareUsageDescription` / `NSHealthUpdateUsageDescription`
     Running on an iOS device will cause immediate app crash upon requesting any of these features.
   - Recommended Correction: Add the required keys with descriptive user-facing rationale strings.
   - Observation: Code inspection of `Info.plist`.

4. [SEVERITY: LOW] Dead Code: SnapTimeRuler Widget
   - File: `lib/widgets/snap_time_ruler.dart` (742 lines)
   - Problem: The horizontal time ruler widget is completely unreferenced by any screen in
     `lib/views/`. It was replaced in `SelectCourtDateSlotScreen` by the 3-column discrete grid.
     Keeping 742 lines of unused complex painting code increases maintenance overhead.
   - Recommended Correction: If the ruler concept is permanently superseded by the 3-column grid,
     archive or delete `snap_time_ruler.dart` and remove its tests from `test/venue_booking_test.dart`.
   - Observation: Code inspection & grep search.

5. [SEVERITY: MEDIUM] Simulated Account Deletion in EditProfileScreen
   - File: `lib/views/edit_profile_screen.dart` (lines 145-164)
   - Problem: When the user confirms "Delete Account", the callback simply displays a SnackBar:
     `'Account deletion request submitted.'` No backend request or Firebase deletion is invoked.
   - Recommended Correction: Connect account deletion to a secure backend endpoint or
     `FirebaseAuth.instance.currentUser.delete()` with re-authentication.
   - Observation: Code inspection.

8. FUNCTIONAL FLOW AUDIT
================================================================================
Detailed walkthrough of core user workflows across the codebase:

1. REGISTRATION & LOGIN FLOW:
   - Starting Screen: `WelcomeScreen` -> `EmailScreen`.
   - Actions: User enters email address and taps "Send Code".
   - State Changes: `_authController.setAuthMode('email')`, `_state.isLoading = true`.
   - Backend Call: `POST /api/request-otp` on `https://tolli-app.onrender.com`.
   - Backend Logic: Validates RFC email regex; checks 60-second cooldown in `otpStore`;
     generates 6-digit random number; stores HMAC-SHA256 hash in memory (5-minute expiry);
     dispatches email via Gmail API OAuth2 (fallback to Brevo/SendGrid/Mailjet/Resend).
   - Client Transition: On success, pushes `OtpScreen`.
   - Verification: User enters 6 digits. `POST /api/verify-otp`.
   - Token Minting: Backend verifies hash; mints Firebase Custom Token via Firebase Admin SDK.
   - Client Auth: `FirebaseAuth.instance.signInWithCustomToken(firebaseToken)`.
   - Onboarding Check: If `isProfileComplete == true` -> `HomeScreen`; else -> `LocationScreen`.
   - Status: 🟢 VERIFIED WORKING for Email OTP & Google Sign-In; 🔴 BROKEN/SIMULATED for Phone OTP.

2. ACTIVITY CREATION FLOW:
   - Starting Screen: `HomeScreen` (tap "+") or `BookingStatusScreen` ("Create Game at Venue").
   - Actions: User selects sport category, date, start time, duration, player count, skill level,
     cost per person, and privacy ("Public" vs "Invite only").
   - State Changes: Validates form inputs in `CreateActivityScreen`.
   - Database Write: `ActivityRepository().createActivity()` writes a new document to
     `/activities/{activityId}` with `hostId = currentUser.uid`, `participantIds = [hostUid]`,
     `status = 'scheduled'`, and server timestamps. If prefilled from a venue booking,
     `linkGameToBooking()` updates the booking with `createdGameId`.
   - Success Condition: Pushes `ActivityCreatedScreen` with confetti/share CTA, then `HomeScreen`.
   - Status: 🟢 VERIFIED WORKING (Covered by `test/activity_lifecycle_test.dart`).

3. JOINING & LEAVING ACTIVITY FLOW:
   - Starting Screen: `ActivityDetailScreen`.
   - Direct Join (Public): User taps "Join Game".
     - Repository Call: `ActivityRepository().joinActivityDirectly()`.
     - Database Action: Atomic Firestore update adds `uid` to `participantIds`, increments
       `joinedPlayers`, and creates document in `/activities/{id}/participants/{uid}`.
     - Result: Navigates to `JoinedScreen`.
   - Request to Join (Invite Only): User taps "Request to Join".
     - Repository Call: `ActivityRepository().requestToJoinActivity()`.
     - Database Action: Creates document in `/activities/{id}/requests/{uid}` with
       `status = 'PENDING'` and writes an in-app notification to host's `/notifications`.
     - Host Action: Host reviews request in `PlayersScreen` or `NotificationsScreen` and taps
       "Accept" or "Decline". On accept, player is moved to `/participants`.
   - Leaving Activity: Confirmed player taps "Leave Activity".
     - Confirmation Dialog: `_showLeaveConfirmationModal()`.
     - Database Action: Atomic transaction removes `uid` from `participantIds`, decrements
       `joinedPlayers`, and deletes document from `/participants/{uid}`.
   - Status: 🟢 VERIFIED WORKING (Covered by `test/activity_lifecycle_test.dart`).

4. UPCOMING ACTIVITIES FILTERING:

9. BOOKING AND PAYMENT ENGINE AUDIT
================================================================================
The booking system is the most critical commercial component of the application.
An extensive audit of all booking models, services, screens, and tests was conducted:

1. ACTIVE BOOKING UI IN USE:
   - The active screen used for venue booking is `SelectCourtDateSlotScreen`
     (`lib/views/select_court_date_slot_screen.dart`).
   - It implements a modern 5-section layout:
     A. Date Selector Strip (`DateSelectorStrip` with 14-day rolling selector).
     B. Court Selection cards with surface type and capacity.
     C. Booking Duration pills (30 min, 1 hour, 1.5 hours, 2 hours, 3 hours).
     D. Available Start Times Grid (clean 3-column discrete grid of 30-minute intervals).
     E. Sticky Bottom Summary ("Continue" button with price and interval).

2. REMAINING OLDER / DUPLICATE WIDGETS:
   - `lib/widgets/snap_time_ruler.dart` (742 lines) remains in the project. It contains an
     elaborate horizontal sliding timeline with day/night theming.
   - VERIFIED FACT: It is NOT used in `SelectCourtDateSlotScreen`. It is only imported in
     `test/venue_booking_test.dart`.

3. START TIME GENERATION & INTERVALS:
   - Generated by `BookingTimeUtils.generateStartTimes()`.
   - Increments: Exactly 30-minute intervals (e.g. 06:00 AM, 06:30 AM, 07:00 AM ...).
   - Bounded by venue operating hours: Slots start at `openMinutes` and terminate at
     `closeMinutes - minDurationMinutes`.

4. DURATION & AVAILABILITY LOGIC:
   - When the user selects a duration (e.g. 90 minutes), every 30-minute start time in the grid
     is evaluated across its entire interval: `[startTime, startTime + duration]`.
   - Evaluation Function: `VenueRepository.evaluateIntervalStatus()`.
   - Rules:
     - If `startTime + duration > closeMinutes` -> status is `EXCEEDS_CLOSING`.
     - If interval overlaps any confirmed booking -> status is `BOOKED`.
     - If interval overlaps any active hold (less than 10 mins old) -> status is `HELD`.
     - If interval is completely clear -> status is `AVAILABLE`.
   - Duration Change Handling: If the user changes duration while a slot was selected,
     `_revalidateSelectedStartTime()` immediately re-evaluates. If the slot is no longer valid,
     it is cleared automatically.

5. PRICE CALCULATIONS:
   - Pricing Formula: Authoritative integer paise calculation:
     `pricePaise = ((court.hourlyRatePaise * durationMinutes) / 60.0).round()`
   - Example (Pickleball at ₹600 / 60,000 paise per hour):
     - 30 minutes = 30,000 paise (₹300).
     - 60 minutes = 60,000 paise (₹600).
     - 90 minutes = 90,000 paise (₹900).
     - 120 minutes = 120,000 paise (₹1,200).
   - Display Consistency: The price displayed on `SelectCourtDateSlotScreen` matches the
     amount in `BookingReviewScreen` and matches the amount calculated by the backend in
     `server/index.js` (lines 950-955).

6. SERVER-SIDE HOLD & VALIDATION:
   - Client calls `POST /api/bookings/prepare-payment`.
   - Server re-validates:
     - Required identifiers (`userId`, `venueId`, `courtId`).
     - Minimum 30 minutes duration.
     - Start time >= opening time.
     - End time <= closing time.
     - Full interval overlap check against candidate bookings in memory and Firestore.
   - Provisional Hold: Placed with `bookingStatus = 'HELD'`, `holdExpiresAt = now + 10 mins`.
   - Razorpay Order: Server calls Razorpay API to generate `razorpayOrderId`.

7. PAYMENT CONFIRMATION & WEBHOOKS:
   - On successful payment, Razorpay SDK invokes `_handlePaymentSuccess()`.
   - `BookingStatusScreen` calls `POST /api/payments/verify`.
   - Backend updates booking status to `CONFIRMED` and payment status to `CAPTURED`.
   - Webhook: `POST /api/webhooks/razorpay` listens to `payment.captured` and `order.paid`
     with atomic deduplication via Firestore `/processed_webhooks/{eventId}`.

8. CRITICAL SECURITY DEFECTS IN PAYMENT:
   - DEFECT 1: In `server/index.js` line 1059:
     ```javascript
     if (razorpaySignature) {
       // verification ...
     } else {
       isValidSignature = true; // <--- CRITICAL BYPASS!
     }
     ```
     If an attacker posts to `/api/payments/verify` with any `bookingId` and omits
     `razorpaySignature`, the server marks the booking as confirmed without payment!
   - DEFECT 2: In `server/index.js` line 1152:
     Webhook signature check only executes `if (signature)`. Missing signature header
     does not return 400, allowing unsigned spoofed webhook calls.

10. BACKEND AND SECURITY AUDIT
================================================================================
- Runtime: Node.js (v24.19.0) with Express framework.
- Main File: `server/index.js` (1354 lines).
- Server Health Check: `GET /` -> `{ status: 'online', service: 'tolii-backend' }`.

API ENDPOINT INVENTORY:
-----------------------
1. `GET /`
   - Purpose: Server health check & pre-warm ping.
   - Auth Required: None.
2. `GET /api/test-transports`
   - Purpose: Diagnostic endpoint to test email provider connectivity.
   - Auth Required: None.
3. `POST /api/request-otp`
   - Parameters: `{ email }`.
   - Validation: Regex check, 60s cooldown per email.
   - Output: `{ success: true, message: 'OTP sent...' }`.
4. `POST /api/verify-otp`
   - Parameters: `{ email, otp }`.
   - Validation: HMAC-SHA256 hash match, 5-min TTL, max 5 attempts.
   - Output: `{ success: true, firebaseToken, uid }`.
5. `POST /api/bookings/prepare-payment`
   - Parameters: `{ userId, venueId, courtId, slotId, bookingDate, startTime, durationMinutes }`.
   - Validation: Operating hours, 30m minimum, interval collisions, hold expiry.
   - Output: `{ success: true, bookingId, razorpayOrderId, amountPaise, keyId, holdExpiresAt }`.
6. `POST /api/payments/verify`
   - Parameters: `{ bookingId, razorpayOrderId, razorpayPaymentId, razorpaySignature }`.
   - Vulnerability: Allows missing signature!
   - Output: `{ success: true, message, booking }`.
7. `POST /api/bookings/:bookingId/release-hold`
   - Parameters: URL param `bookingId`.
   - Action: Releases hold if status is `HELD`.
8. `POST /api/webhooks/razorpay`
   - Parameters: Raw body webhook payload.
   - Action: Deduplicates event ID, updates Firestore booking record.
9. `POST /api/bookings/:bookingId/cancel`
   - Parameters: URL param `bookingId`, body `{ userId }`.
   - Action: Calculates refund percentage based on cancellation window; calls Razorpay refund API.

SECURITY VULNERABILITIES & CODE SMELLS:
--------------------------------------
1. [CRITICAL] Payment Signature Bypass in `/api/payments/verify` (line 1059).
2. [CRITICAL] Webhook Missing Signature Bypass in `/api/webhooks/razorpay` (line 1152).
3. [HIGH] Fallback hardcoded credentials in `server/index.js`:
   - `RAZORPAY_KEY_ID = process.env.RAZORPAY_KEY_ID || 'rzp_test_TOLII_VENUE_KEY'`
   - `RAZORPAY_KEY_SECRET = process.env.RAZORPAY_KEY_SECRET || 'tolii_razorpay_secret_key_2026'`
   - `RAZORPAY_WEBHOOK_SECRET = process.env.RAZORPAY_WEBHOOK_SECRET || 'tolii_webhook_secret_2026'`
   - `OTP_SECRET = process.env.OTP_SECRET || 'tolii_secure_secret_salt_2026'`
   If environment variables fail to load on Render, the server silently falls back to these
   well-known strings instead of crashing or throwing configuration errors.
4. [MEDIUM] Lack of Global Rate Limiting: No `express-rate-limit` package installed. Endpoints
   like `/api/bookings/prepare-payment` and `/api/verify-otp` could be spammed.
5. [MEDIUM] In-Memory State Loss: `otpStore` and `inMemoryBookingsStore` use JavaScript `Map`.
   When Render spins down or restarts the free web service, all unexpired OTPs and active holds
   are wiped.
